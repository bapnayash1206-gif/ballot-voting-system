# DynamoDB Data Model — Stage 2 Design Only

**Project:** Real-Time Voting System Using AWS Serverless Architecture
**Status:** Logical design plus local AWS integration preparation; no AWS resources or deployed backend have been created.
**Scope:** The local React/Vite frontend and mock API remain the runnable application. `aws/` contains un-deployed handler and SAM preparation.

## 1. Design summary

Use one DynamoDB table, provisionally named `BallotData`, with string partition and sort keys `PK` and `SK`. The table stores poll metadata, ballots, sharded result counters, chat messages, and WebSocket connection records as different item types. Key prefixes include the poll ID so records and queries remain scoped to that poll.

Use sparse GSI `GSI1` for both owner-scoped admin lists and a voter discovery directory. Poll metadata items use `GSI1PK=OWNER#<verifiedOwnerSubject>`; separate `DISCOVERY` items for polls started at least once use `GSI1PK=VOTER#AVAILABLE`. The voter directory contains poll IDs and ordering keys, not vote totals; the backend reads authoritative poll metadata and omits counts. Draft polls have no discovery item. Active, closed, and expired polls remain available to authenticated voters; expired status is derived from the server clock. The same GSI supports both access patterns, so the SAM IAM resource scope does not need a new index permission. GSI reads are eventually consistent, so recently published or transitioned polls may appear briefly late; the backend rechecks base-table metadata. This global directory partition is suitable only for the current small demo and can become a hot partition at scale. See [DynamoDB read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html) and [GSI behavior](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/GSI.html).

This is a logical proposal, not a claim that the application is secure, deployed, or real-time. The table, indexes, backend routes, authorizer, and WebSocket API remain future work.

## 2. Table and item keys

| Item type | `PK` | `SK` | Important attributes |
|---|---|---|---|
| Poll metadata | `POLL#<pollId>` | `META` | `ownerSub`, `tenantId`, `question`, `options[]`, `status`, `votingType`, `votingMode`, `durationSeconds`, `startsAt`, `endsAt`, `resultVisibility`, `chatEnabled`, `createdAt`, `updatedAt`, `schemaVersion`, `voteShardCount`, `resultShardCount`; sparse GSI owner keys |
| Voter discovery directory | `POLL#<pollId>` | `DISCOVERY` | `pollId`, `createdAt`; `GSI1PK=VOTER#AVAILABLE`, `GSI1SK=POLL#<createdAt>#<pollId>`; created on first start and refreshed on lifecycle changes |
| Ballot | `POLL#<pollId>#VOTES#<voteShard>` | `VOTER#<voterKey>` | `pollId`, `voterKey`, `voteData`, `submittedAt`, `schemaVersion` |
| Result counter shard | `POLL#<pollId>#RESULTS#<resultShard>` | `TOTALS` | `pollId`, `ballotCount`, `optionCounts` map keyed by stable option ID, `updatedAt` |
| Final result snapshot (optional) | `POLL#<pollId>` | `RESULTS#FINAL#<version>` | `ballotCount`, `optionCounts`, percentages or enough counts to derive them, `computedAt`, `algorithmVersion` |
| Chat message | `POLL#<pollId>#CHAT#<YYYYMM>` | `MSG#<ISO-8601 timestamp>#<messageId>` | `pollId`, `messageId`, `senderDisplay`, `text`, `createdAt` |
| Connection registry | `CONNECTION#<connectionId>` | `STATE` | `connectionId`, `pollId`, optional authenticated subject, `connectedAt`, `expiresAt` (TTL epoch seconds) |
| Poll connection membership | `POLL#<pollId>#CONNECTIONS#<connectionShard>` | `CONNECTION#<connectionId>` | `pollId`, `connectionId`, `expiresAt` (TTL epoch seconds) |

`pollId` and option IDs should be generated by the trusted backend and treated as immutable identifiers. Store options as objects such as `[{ optionId, label, position }]`, not just labels, so renamed options do not change the meaning of historical ballots. Freeze option IDs and labels once votes are accepted, or version the ballot schema if edits after opening are ever allowed.

`votingType` is one of `single`, `multiple`, or `ranked`. `votingMode` is `public` or `anonymous`. `resultVisibility` is `live`, `afterVote`, or `afterClose`. Poll state should be explicit (`draft`, `active`, `closed`); expiration is evaluated by the backend against `endsAt` and should not depend on the browser countdown.

### Sharding

Store `voteShardCount` and `resultShardCount` on the poll when it is created. A deterministic hash of the poll-scoped `voterKey`, modulo the configured count, selects both its ballot partition and result-counter partition. This distributes high-volume writes across partition keys while keeping each key prefixed with that poll ID. Choose shard counts from expected traffic and load tests; a value such as 16 can be an initial sizing hypothesis, not a performance guarantee. Keep the shard count stable during an active poll, or define a migration/versioning plan before changing it.

For a small class demo, fewer shards may be simpler. Sharding adds fan-out reads: results sum all result shards, and full ballot scans for a poll query each vote shard. Avoid DynamoDB `Scan` for normal poll access.

## 3. GSI for owner management and voter discovery

Proposed sparse index:

- Poll metadata: `GSI1PK = OWNER#<verifiedOwnerSubject>`, `GSI1SK = POLL#<createdAt>#<pollId>`.
- Discovery directory: `GSI1PK = VOTER#AVAILABLE`, `GSI1SK = POLL#<createdAt>#<pollId>`.

Admin list requests query only the owner partition derived from the verified subject. Voter discovery queries the directory partition, then loads each poll's base-table metadata. The endpoint excludes drafts and includes active, closed, and expired polls; result visibility is still enforced by the results API. The directory item is created when a draft is started and transactionally refreshed with each lifecycle change. Poll metadata remains owner-indexed for admin management. If the product becomes tenant-managed, use a verified tenant key and explicit ownership checks. GSI propagation is asynchronous, so discovery is eventually consistent; a base-table read is authoritative.

Keep the index count small. Every additional index adds storage and write work; do not add indexes for access patterns the app does not need.

## 4. Required access patterns

1. **Load a poll by link:** `GetItem(PK=POLL#id, SK=META)`; verify status, time window, and caller permissions on the backend.
2. **List polls for an admin:** paginated `Query` on `GSI1` using the verified owner or tenant partition key.
3. **Discover voter-facing polls:** paginated `Query` on `GSI1` using `VOTER#AVAILABLE`, then base-table `GetItem` for each poll; never return draft polls or result counts from this path.
4. **Prevent a voter's second ballot:** derive the same poll-scoped `voterKey` and deterministic vote shard, then `GetItem` the exact `VOTER#voterKey` key when necessary for an explanatory response. The authoritative duplicate check is the conditional `Put` in the transaction below, not this preliminary read.
5. **Submit a ballot and update results:** one transaction checks poll state, conditionally inserts the unique ballot, and increments the selected result shard.
6. **Read poll totals:** query each known result-shard partition and sum its `ballotCount` and per-option counts. For current results, read the base table, not the GSI.
7. **Read recent chat:** query the relevant poll/month partition with `begins_with(SK, 'MSG#')`, descending and paginated. If the requested range crosses a month boundary, query each month partition and merge by timestamp.
8. **Find all connections for a poll:** query its connection-shard partitions and page through `CONNECTION#` records. Use `expiresAt > now` as an application-side filter; a TTL deletion is not immediate.
9. **Clean up a disconnected connection:** `GetItem(PK=CONNECTION#connectionId, SK=STATE)` to learn its poll and shard, then delete both the registry and poll-membership records.

## 5. Safe concurrent voting and duplicate prevention

### Ballot identity

A browser-supplied voter ID is not trustworthy. The backend must derive `voterKey` from a verified identity or a trusted one-time voting credential, scoped to the poll. For example, it can be a keyed pseudonym derived from `(pollId, verifiedSubject)` so the table does not need to store a raw email or account ID in every ballot. The key-generation secret must stay in trusted backend configuration, never in React code.

“Anonymous” should mean that ballot items do not contain directly identifying voter information. It does not mean a visitor can obtain multiple votes anonymously without limit. If the product does not authenticate voters or issue trusted one-time credentials, duplicate-vote prevention can only be best-effort and can be bypassed by changing browsers/devices. Eligibility and anonymity policy must be decided before implementation.

### Atomic submit transaction

For a submission, validate option IDs and voting type on the backend, derive `voterKey`, and use one DynamoDB `TransactWriteItems` request containing three different items:

1. **ConditionCheck** `POLL#id / META`: poll status is `active` and `endsAt` is after the server's current time. This prevents the browser clock from authorizing a late vote.
2. **Put** the ballot under its deterministic vote shard with `ConditionExpression: attribute_not_exists(PK)`. This makes the first ballot for that poll-scoped voter key win.
3. **Update** the corresponding result-counter shard: atomically increment `ballotCount` once and increment each selected option's count once.

DynamoDB transactions commit all actions or none; therefore a duplicate or closed-poll failure cannot leave a ballot without its count, or increment a count without saving its ballot. DynamoDB also requires transaction actions to target distinct items, which is why poll metadata and result counters are separate items. See [TransactWriteItems](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html) and [DynamoDB transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transactions.html).

Use an SDK `ClientRequestToken` for safe retries of an identical request within DynamoDB's idempotency window, and retain the conditional ballot key as the durable duplicate barrier. Return a clear “already voted” response for the ballot condition failure; distinguish it from a poll-closed condition failure without exposing internal data.

Concurrent distinct votes update counters with atomic numeric increments, so one update does not overwrite another. A stable hash distributes those writes among result shards. A race between voting and closing is resolved by the transaction condition: a vote whose transaction commits while the poll is active is counted; a close that wins first causes later vote transactions to fail. Closing should update the poll metadata through a conditional backend write and then finalize results.

These guarantees depend on all vote writes going through the trusted backend transaction. Direct browser access to DynamoDB would defeat the rules.

## 6. Vote record shapes and voting rules

- **Single choice:** `voteData = { selectionId: "OPT#..." }`. Require exactly one valid option ID.
- **Multiple choice:** `voteData = { selectionIds: ["OPT#...", ...] }`. Require at least one valid, distinct option ID. Increment `ballotCount` once and each selected option count once.
- **Ranked choice (IRV):** `voteData = { rankedOptionIds: ["OPT#...", "OPT#...", ...] }`, ordered from first to last preference. A ranking must contain at least one valid poll option ID, with no duplicates. Partial rankings are allowed; unranked options mean the voter has no further preference among them.

Votes should be immutable for the initial design. If vote changes are allowed later, define whether the last ballot wins and update the old and new option counters in one transaction; do not simply overwrite the ballot while leaving prior counters unchanged.

## 7. Results and percentage calculations

The result shards are the transactional aggregate. `ballotCount` counts accepted ballots, not selected options. For each option:

`percentage = optionCount / ballotCount * 100`

Return zero percentages when `ballotCount` is zero. Round only for display; calculate from integer counts. For **multiple choice**, percentages mean “share of submitted ballots that selected this option,” so the option percentages can add up to more than 100%. For **single choice**, totals should sum to 100% before display rounding when every ballot has one valid choice.

The `RESULTS#FINAL#version` item is an optional immutable snapshot written after the poll is closed, after summing the result shards. Include an algorithm/version field so a ranked tally can be reproduced. The transactional shards remain the source of truth for accepted ballot count and single/multiple-choice counts; ranked results must read the ordered ballot records because option counters do not encode preference transfers. A consistency audit can periodically compare aggregate counts to accepted ballot records and flag discrepancies.

For live visibility, the results handler reads/sums current base-table shards. For `afterVote`, it must verify the requester's accepted ballot before returning them. For `afterClose`, it returns only after a trusted backend confirms the poll is closed. The frontend visibility setting alone is not an access control.

## 8. Ranked-choice counting (IRV)

The local backend and AWS handler use the same IRV implementation. Each accepted ballot stores `voteData.rankedOptionIds`; the backend calculates the result from ballots and never accepts client-supplied totals.

Rules:

1. A ballot ranks at least one valid candidate, each at most once. It may omit candidates; omitted candidates are not preferences.
2. Each round assigns a ballot to its highest-ranked candidate who remains active. If none remain, that ballot is exhausted.
3. A candidate wins only with a strict majority (`votes > continuing ballots / 2`). Exhausted ballots are excluded from the continuing-ballot denominator.
4. If there are no submitted ballots, the outcome is `no_votes`. If no ballots continue, the outcome is `no_continuing_ballots`.
5. Without a majority, a uniquely lowest candidate is eliminated. If two or more candidates share the lowest tally, counting stops with `elimination_tie`; the tied candidates are reported and there is no winner. No ID, option order, randomness, or other arbitrary tie-break is used.
6. Results include round tallies, continuing and exhausted ballot counts, elimination/tie information, outcome, and algorithm version.

Ranked results query every poll vote shard and recalculate each time they are requested. This is correct for the current scaffold but may become costly or slow for large polls. A future scale-up could compute a versioned final snapshot after close; that would require an explicit process/resource design and is not included here. No DynamoDB table or index change is required for the current ballot shape. Existing `Query` permission on the table supports the vote-shard reads; no new IAM action is required.

## 9. Poll chat and WebSocket connection records

DynamoDB stores connection membership and messages; it does **not** push updates to browsers by itself. A future API Gateway WebSocket API would handle `$connect`, message routes, and `$disconnect`. On connect, backend code validates the poll and caller, then transactionally writes the connection registry and poll-membership item. Use a deterministic connection shard if a poll may have many simultaneous connections.

When chat is enabled, a backend message route validates the poll and message, writes the message under its poll/month partition, then queries that poll's live connection memberships and calls the API Gateway Management API `PostToConnection` for each active connection. Remove records on `$disconnect` and when `PostToConnection` returns a gone connection. AWS documents the WebSocket callback management API at [Use @connections commands](https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-how-to-call-websocket-api-connections.html) and the WebSocket API lifecycle at [WebSocket API overview](https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-websocket-api-overview.html).

Use DynamoDB TTL only as a cleanup fallback for connection records, with Unix epoch seconds in a numeric attribute. TTL cleanup is asynchronous and may take days, so it must not be treated as immediate disconnect or authorization. See [DynamoDB TTL](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html).

## 10. Backend authorization requirements

DynamoDB key design does not authorize an administrator. The current local AWS scaffold uses these rules:

- API Gateway's JWT authorizer validates the OIDC token; handlers use its verified `sub`. The backend-only `GOOGLE_ADMIN_SUBJECTS` allowlist assigns admin capability. Google account claims and browser-supplied roles do not grant admin access.
- Every poll create/update/start/close/reopen/delete operation requires an allowlisted subject. Existing-poll mutations also require `ownerSub` to equal that verified subject. An allowlisted admin cannot manage another owner's poll.
- Authenticated non-admin callers discover only published (started) polls. Direct reads hide drafts except from their allowlisted owner. Vote, results, chat, and WebSocket routes separately check status, visibility, chat setting, verified subject, and poll scope.
- Voting eligibility currently means a valid authenticated OIDC subject plus the poll's active window and one-ballot-per-subject-per-poll rule. There is no campus roster/domain allowlist or per-poll eligible-voter list yet; add and test that policy before real campus use if required.
- The browser must never receive AWS credentials or direct table write permissions. Backend execution roles should have only the table/index operations each handler needs.
- Separate admin-only and voter-facing behavior in backend authorization; hiding an admin button in React is not protection.

The identity provider and authorizer choice is intentionally not configured here.

## 12. AWS preparation addendum

The local-only implementation preparation in `aws/` keeps this table/key design and adds these concrete choices:

- A separate API Gateway **HTTP API** handles the existing CRUD, lifecycle, vote, receipt, result, chat-history, and one-time WebSocket-ticket HTTP operations. A WebSocket API cannot replace these HTTP request/response routes.
- The HTTP API requires a JWT from Google OIDC. Cognito is not included. Admin mutations require the backend-only `GOOGLE_ADMIN_SUBJECTS` verified-subject allowlist and verify `ownerSub` in the repository; there is no frontend role authority.
- `GET /polls` defaults to the owner-scoped admin list for allowlisted admins and published voter discovery for other authenticated callers. `?view=voter` explicitly requests voter discovery (including for an admin using the voter portal); `?view=admin` requires an allowlisted subject. Voter discovery lists started polls (active, closed, or expired) but never drafts or vote totals. Direct reads of draft metadata require the owning allowlisted admin.
- The WebSocket `$connect` route consumes a 90-second, one-use ticket stored in this table. The ticket is minted only by an authenticated HTTP request. This avoids putting a long-lived bearer token in the WebSocket URL; the short-lived ticket still appears in that URL and should not be logged.
- Result updates send only a poll-scoped `results.updated` event. Clients then call the authenticated HTTP results route, which rechecks visibility before returning counts. The WebSocket handler reads poll ID and purpose from the trusted connection context, not from a client-supplied destination ID.
- Connection registry and poll-membership items are written/deleted transactionally. `expiresAt` TTL is cleanup assistance only; handlers also filter expired entries because TTL deletion is asynchronous.
- Dashboard metadata pages through the owner GSI and reads result shards to compute owner-scoped totals. This is deliberately simple for a small project but costs approximately one result-shard read per poll per dashboard load, in addition to GSI reads. It is not a high-scale dashboard strategy. Voter discovery uses separate directory items in the existing GSI1; that single shared partition is a small-demo choice and needs sharding/review before scale.
- Vote transactions keep the poll condition check, conditional ballot insertion, and result-shard update as separate items. A verified OIDC `sub` is transformed into a poll-scoped HMAC voter key. Changing the HMAC secret without a versioned migration would break the duplicate-key lookup, so the secret must remain stable until a migration plan exists.
- The initial REST/WebSocket API configuration requires authentication for all application routes except health. “Anonymous” voting therefore means the ballot record omits the raw account subject; it does not mean an unauthenticated visitor can vote. A trustworthy public unauthenticated mode would require a separately designed, single-use eligibility-token system.

These choices are not deployed or validated against live AWS services. The deployment guide lists remaining frontend/provider and product decisions.

## 11. Limitations and decisions before implementation

- No AWS resources, backend, identity provider, credentials, or WebSocket API were created or configured.
- A single-vote rule requires a stable trusted voter identity or one-time credential. Truly unauthenticated anonymous voting cannot robustly prevent repeat voters.
- Shard counts and retention periods need expected traffic and institutional policy; this proposal makes no throughput or cost guarantee.
- Poll option changes after ballots exist can make results ambiguous; freeze or version options.
- Ranked-choice method and tie rules remain product decisions.
- Chat retention, moderation, and sender identity policy are not defined.
- Owner-list GSI reads can lag. Use base-table reads for authoritative poll state and results.
- TTL is delayed cleanup, not an exact expiration mechanism.
- Vote counters are exact only if every accepted ballot and counter increment uses the described transaction. Administrative repairs must use audited backend tooling.
